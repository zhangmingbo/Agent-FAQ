# Qoder 开发效率复盘与规范建议

> 基于 FAQ 智能问答机器人项目（v1.0 → v5.0）的完整开发历程

---

## 二、详细问题清单与根因分析

### 2.1 上下文/记忆丢失（效率杀手 #1）

| # | 问题 | 根因 | 浪费轮次 |
|---|------|------|---------|
| 1 | 新会话记忆不带过来，需重新告知项目背景 | 会话隔离机制 | 3-5轮/次 |
| 2 | 遗忘数据库名（faqdb）、服务器地址等已告知信息 | 记忆未持久化或未检索 | 2-3轮/次 |
| 3 | 遗忘 .env 配置项（JWT_SECRET、ADMIN_PASS） | 跨会话信息丢失 | 3-4轮/次 |
| 4 | 遗忘开发与云环境共享同一数据库 | 关键架构决策未记录 | 2轮/次 |
| 5 | 用户情绪："这些原来跟你说过的你咋都忘了呢" | 以上问题的累积效应 | — |

**根因**：Qoder 的记忆系统依赖会话内上下文，跨会话时若未主动持久化到 Memory 系统，信息会丢失。

---

### 2.2 前端构建/部署（返工最多）

| # | 问题 | 根因 | 修复次数 |
|---|------|------|---------|
| 1 | Vue SPA 只有构建产物无源码，无法直接修改 | 源码目录不在工作区 | 1次（决定新建） |
| 2 | Element Plus 表格百分比宽度失效，列挤在一起 | 组件库限制 | 3次迭代 |
| 3 | FaqManage → CategoryTree prop 名不匹配（tree vs treeData） | 组件接口不一致 | 2次迭代 |
| 4 | 事件名不匹配（onSelect vs onUpdate:modelValue） | Vue 3 emit 命名约定 | 1次 |
| 5 | 登录页显示侧边栏 | App.vue 布局未区分路由 | 1次 |
| 6 | 前端构建后 JS 哈希变更（B6k5iYoY → B7TVzcyY），HTML 未同步 | 构建产物哈希机制 | 1次 |
| 7 | CSS 哈希引用不匹配致样式丢失 | 同上 | 1次 |
| 8 | 分类徽章对齐/溢出问题反复修改 | 无截图验证闭环 | 4次迭代 |
| 9 | 前端文件上传到服务器错误子目录（dist/嵌套） | 部署路径说明不清晰 | 2次 |

**根因**：
- 修改编译后产物（非源码）导致修复困难、容易引入新问题
- 缺少"修改→构建→验证"的闭环流程
- UI 问题依赖截图反馈，无自动化视觉验证

### 2.3 Docker/运维（耗时最长）

| # | 问题 | 根因 | 耗时 |
|---|------|------|------|
| 1 | 模型不匹配：代码默认 paraphrase，镜像只有 bge-base | 代码与镜像不同步 | 10分钟 |
| 2 | Docker push 失败：HTTPS/HTTP 协议不匹配 | insecure-registries 配置格式错误 | 30分钟 |
| 3 | Zot 仓库大镜像推送失败：blob upload unknown | 大层上传超时 | 20分钟 |
| 4 | VPN 干扰 Docker 连接 | 网络代理冲突 | 15分钟 |
| 5 | 容器启动失败：缺少 JWT_SECRET 和 ADMIN_PASS | .env 配置不完整 | 10分钟 |
| 6 | 增量部署文件放到错误子目录 | 路径说明不清晰 | 15分钟 |
| 7 | scp 无法自动输入密码 | Bash 工具限制 | 10分钟 |

**根因**：
- 无标准化部署流程，每次手动操作易出错
- 网络环境（VPN/代理）影响工具链
- 增量 vs 全量策略不清晰

| 4 | 文件删除存在路径穿越风险（../../etc/passwd） | 🔴 严重 | 架构审查 |

| 7 | ruleLoader setInterval 未清理，内存泄漏 | 🟡 中等 | 架构审查 |
| 8 | _logChat 重复执行无意义检测 | 🟡 中等 | 日志分析 |
| 9 | health.js 未用 asyncHandler 包裹 | 🟡 中等 | 架构审查 |

| 13 | 无意义检测因数据库空配置覆盖默认规则而失效 | 🔴 功能 | 功能测试 |

**根因**：
- 项目早期缺乏代码审查和安全扫描
- 部分逻辑依赖数据库配置，但配置可能为空/异常

## 四、改进建议

### 4.1 记忆/上下文管理（优先级：🔴 最高）

**问题**：跨会话信息丢失是最大效率杀手。

**建议**：

```
✅ 每次会话开始时，主动检索并加载项目记忆
✅ 关键配置（DB地址、密码、服务器IP）必须持久化到 Memory
✅ 架构决策（共享数据库、部署方式）必须记录
✅ 建立项目级 Memory 模板，新会话自动加载
```

**具体做法**：
1. 创建 `project_introduction` 类型的 Memory，包含：服务器地址、数据库名、部署方式、.env 关键配置
2. 每次新会话开始，先 `SearchMemory` 加载项目上下文
3. 用户告知的配置信息，立即 `UpdateMemory` 持久化

---

### 4.2 前端开发流程（优先级：🔴 高）

**问题**：修改编译产物导致修复困难。

**建议**：

```
✅ 永远在源码层修改，修改后必须执行构建
✅ 建立"修改→构建→验证"三步闭环
✅ 构建后自动检查 HTML 中的哈希引用是否同步
✅ UI 问题必须截图验证，不能假设修复成功
```

**具体做法**：
1. 确认 Vue 源码目录（`frontend/`）始终在工作区内
2. 修改 `.vue` 文件后，立即执行 `npm run build`
3. 构建完成后，自动对比 `dist/index.html` 与 `public/admin/index.html` 的哈希引用
4. 部署到服务器后，通过 SSH 验证页面是否正常

---

### 4.3 Docker 部署标准化（优先级： 高）

**问题**：每次部署都是手动操作，容易出错。

**建议**：

```
✅ 使用 deploy/ 目录的标准化部署包
✅ 建立"构建→导出→传输→加载→验证"五步流程
✅ 增量更新和全量更新有明确判断标准
✅ .env 配置检查前置（启动前验证必需项）
```

**判断标准**：
- **增量更新**：仅前端/静态资源变更 → 基于已有镜像 COPY 新文件
- **全量更新**：依赖变更、模型变更、代码结构变更 → 完整 rebuild

---

### 4.4 代码质量保障（优先级： 中）

**问题**：13 个 Bug 中多个是架构审查才发现的。

**建议**：

```
✅ 新功能开发后，执行架构审查清单
✅ 数据库操作必须参数化，禁止字符串拼接
✅ 文件操作必须校验路径，防止穿越
✅ 配置读取必须有默认值兜底
✅ 定时器必须在 shutdown 时清理
```

**审查清单**：
- [ ] SQL 是否全部参数化？
- [ ] 文件路径是否校验？
- [ ] 配置缺失是否有默认值？
- [ ] 除零风险是否处理？
- [ ] 定时器/连接是否在关闭时清理？
- [ ] 敏感信息是否从环境变量读取？

---

### 4.5 部署流程标准化（优先级：🔴 高）

**已解决**：`deploy/` 目录已建立完整部署包。

**流程**：
```
首次部署：
  1. 复制 deploy/ 到服务器
  2. cp .env.example .env && 修改配置
  3. mysql < init.sql
  4. ./deploy.sh

更新部署：
  1. 本地 docker build
  2. docker save → scp 传输
  3. 服务器 docker load + restart
```

## 五、Qoder 使用最佳实践

### 5.1 会话管理

| 实践 | 说明 |
|------|------|
| **会话开始时加载上下文** | 主动检索项目记忆，不要等用户重复告知 |
| **关键信息立即持久化** | 用户告知的配置、决策，立即保存到 Memory |
| **长任务使用 TodoWrite** | 多步骤任务用任务列表跟踪进度 |
| **跨会话交接** | 会话结束前总结当前状态，便于下次继续 |

### 5.2 代码修改

| 实践 | 说明 |
|------|------|
| **先读后改** | 修改前完整阅读相关文件，理解上下文 |
| **源码层修改** | 永远修改源码，不修改构建产物 |
| **修改后验证** | 代码修改后必须构建+测试，不能假设成功 |
| **小步提交** | 每个修复独立提交，便于回滚 |

### 5.3 部署运维

| 实践 | 说明 |
|------|------|
| **标准化部署包** | 使用 deploy/ 目录，不要每次手动拼凑 |
| **构建前检查** | 确认代码与镜像配置一致（如模型名称） |
| **部署后验证** | 健康检查 + 页面验证，不能只看容器状态 |
| **增量优先** | 小变更用增量构建，节省时间 |

### 5.4 问题排查

| 实践 | 说明 |
|------|------|
| **先看日志** | 容器/服务异常时，先查日志再猜测 |
| **远程验证** | 通过 SSH 直接检查服务器状态，不要让用户截图 |
| **闭环验证** | 修复后必须验证，不能修复完就结束 |
| **根因分析** | 不只修表面问题，要找到根本原因 |

## 六、后期范式总结

### 6.1 开发流程四阶段

```
阶段1: 需求理解
  → 检索项目记忆，加载上下文
  → 理解需求，确认方案
  → 创建任务列表

阶段2: 编码实现
  → 源码层修改
  → 小步提交
  → 本地验证

阶段3: 构建测试
  → 前端构建 + 哈希同步
  → 后端测试 + 接口验证
  → Docker 构建（如需要）

阶段4: 部署验证
  → 标准化部署包
  → 远程验证（SSH）
  → 健康检查 + 页面验证
```

### 6.2 关键原则

1. **记忆优先**：跨会话信息必须持久化，不要让重复沟通浪费轮次
2. **源码为本**：永远在源码层修改，构建产物只是输出
3. **验证闭环**：修改→构建→部署→验证，每一步都不能跳过
4. **标准流程**：使用 deploy/ 部署包，不要每次手动操作
5. **主动检索**：遇到问题先查记忆和代码，不要问用户已知信息
