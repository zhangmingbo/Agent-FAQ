## 一、业界产品核心设计理念提炼

### 1.1 四款产品关键能力对比

| 维度 | Botpress | Genesys Architect | Coze | Dify |
|---|---|---|---|---|
| **变量体系** | temp/session/user/bot/workflow/config 六级作用域 | Flow/Task 级变量，强类型 | 本地/全局/用户级 + 数据库表 | 上下文变量（节点间数据流） |
| **节点类型** | Text/Choice/Execute Code/Capture Info/AI Task/Knowledge/Execute Flow | Ask for Intent/Yes-No/Decision/Call Data/Play Audio/Update Data/Transfer | Start/End/LLM/Plugin/Code/Condition/Loop/Variable/Switch | LLM/Knowledge/Classifier/Condition/Loop/Code/HTTP/Variable/Agent |
| **AI 融合** | Autonomous Engine（LLM 推理 + 结构化逻辑混合） | NLU 内置意图识别 + 知识库 | LLM 节点 + 插件 | Agent Node + Agent Strategy（ReAct/Function Calling） |
| **异常处理** | 兜底逻辑可配置 | No Input/No Match 重试集合 + 最大次数 | 条件兜底 | 节点级错误处理 |
| **子流程** | Execute Flow | Call Bot Flow + Reusable Tasks | 工作流嵌套 | Workflow 调用 |
| **可观测性** | 对话模拟器 + Debugger | 发布前验证 | 执行轨迹 | 执行树 + Token 统计 |

### 1.2 核心设计理念共识

从四款产品中提炼出 **5 条核心设计原则**：

1. **变量作用域分层**：不同生命周期的数据必须隔离（单轮/会话/用户/全局），这是流程编排的基石
2. **节点即契约**：每个节点有明确的输入/输出参数定义，类型安全，类似函数签名
3. **确定性与灵活性分层**：关键路径用结构化节点（条件、循环、动作）保证可控，非关键路径交给 LLM 自主决策
4. **异常是一等公民**：No Match、No Input、超时、校验失败都应有独立分支和重试策略
5. **编排与执行分离**：前端画布产出标准 DSL JSON，后端执行器解析执行，前后端解耦

## 二、当前项目现状与差距

### 2.1 现有 TaskFlow v2 能力

- 节点类型：`collect / confirm / action / branch / message / subtask / end`
- 状态机：`idle → collecting → confirming → executing → done/cancelled/transferred`
- 变量：仅有 `slots`（收集型槽位），无作用域概念
- 分支：`when.slot / when.op / when.value` 单条件
- 意图：触发词 + 向量模型仲裁

### 2.2 核心差距

| 差距 | 影响 |
|---|---|
| 变量只有 slots，无作用域分层 | 无法跨任务共享、无法持久化用户偏好 |
| 无 LLM 节点 | 意图分类、数据提取、文案生成都硬编码在后端 |
| 无代码节点 | 复杂业务逻辑只能改后端代码发布 |
| 无知识库节点 | RAG 未融入流程编排 |
| 异常处理不完整 | No Match 只有简单重问，无重试计数和降级分支 |
| 无发布/版本机制 | 编辑即生效，无法灰度/回滚 |
| 可观测性弱 | 无执行轨迹可视化 |

## 三、设计方案

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    前端编辑器 (Vue 3)                     │
│   Vue Flow 画布 ←→ flowConverter ←→ DSL JSON v3          │
└──────────────────────────┬──────────────────────────────┘
                           │ REST API
┌──────────────────────────▼──────────────────────────────┐
│                    后端执行引擎                           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ 变量引擎  │  │ 节点注册  │  │ 状态机   │  │ 执行追踪  │ │
│  │ (4级作用域)│  │ 中心     │  │ (扩展)   │  │ (Trace)  │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐               │
│  │ NLU 引擎  │  │ LLM 客户端│  │ HTTP 节点│               │
│  └──────────┘  └──────────┘  └──────────┘               │
└──────────────────────────┬──────────────────────────────┘
                           │
                    ┌──────▼──────┐
                    │  MySQL 存储  │
                    └─────────────┘
```

### 3.2 变量体系设计（核心基石）

借鉴 Botpress 的六级作用域，结合项目实际精简为 **四级作用域**：

| 作用域 | 生命周期 | 存储位置 | 典型用途 |
|---|---|---|---|
| `temp` | 单轮对话内 | 内存 | 节点间临时传递数据 |
| `session` | 当前会话 | task_instance.slots JSON | 会话内共享（订单号、用户选择） |
| `user` | 跨会话持久化 | 新增 user_profile 表 | 用户偏好、历史记录 |
| `global` | 全机器人 | sys_config / 新增 bot_var 表 | 全局常量（客服电话、营业时间） |

**变量定义结构**：
```json
{
  "name": "order_id",
  "scope": "session",
  "type": "string",
  "default": null,
  "description": "订单编号"
}
```

**支持类型**：`string / number / boolean / object / array / enum`

**引用语法**（模板字符串）：
- `{{session.order_id}}` — 会话变量
- `{{user.phone}}` — 用户变量
- `{{temp.llm_result.text}}` — 临时变量
- `{{global.service_phone}}` — 全局变量

### 3.3 节点体系设计

#### 3.3.1 节点分类与清单

| 分类 | 节点类型 | 说明 |
|---|---|---|
| **流程控制** | `start` / `end` / `branch` / `switch` / `loop` | 流程路由与循环 |
| **对话交互** | `message` / `collect` / `confirm` | 发消息、收集槽位、确认 |
| **AI 能力** | `llm` / `knowledge` / `intent` | LLM 调用、知识库检索、意图分类 |
| **数据处理** | `set_variable` / `code` / `http` | 变量赋值、代码执行、HTTP 请求 |
| **业务动作** | `action` / `subtask` / `handoff` | 执行业务动作、调用子流程、转人工 |

#### 3.3.2 核心节点 DSL 定义

每个节点统一结构：
```json
{
  "id": "node_xxx",
  "type": "collect",
  "name": "收集手机号",
  "position": { "x": 100, "y": 200 },
  "data": { ... },
  "next": "node_yyy",
  "error_next": "node_error_handler"
}
```

**关键节点详细定义**：

**① collect（收集节点）— 增强版**
```json
{
  "type": "collect",
  "data": {
    "variable": { "name": "phone", "scope": "session", "type": "string" },
    "prompt": "请输入您的手机号",
    "extract": {
      "method": "regex",
      "rule": "1[3-9]\\d{9}"
    },
    "validation": {
      "max_retries": 3,
      "retry_prompts": ["手机号格式不对，请重新输入", "请输入11位手机号"],
      "on_exceeded": "handoff"
    }
  }
}
```

**② branch（分支节点）— 增强为多条件**
```json
{
  "type": "branch",
  "data": {
    "conditions": [
      { "expr": "{{session.age}} >= 18", "next": "node_adult" },
      { "expr": "{{session.age}} < 18", "next": "node_minor" }
    ],
    "default_next": "node_default"
  }
}
```

**③ llm（LLM 节点）— 新增**
```json
{
  "type": "llm",
  "data": {
    "prompt": "请将以下文本分类为: 投诉/咨询/建议\n文本: {{session.user_input}}",
    "model": "deepseek-chat",
    "temperature": 0.3,
    "output_variable": { "name": "intent", "scope": "temp" },
    "output_format": "json"
  }
}
```

**④ knowledge（知识库节点）— 新增**
```json
{
  "type": "knowledge",
  "data": {
    "query": "{{session.user_input}}",
    "kb_id": "faq_main",
    "top_k": 3,
    "threshold": 0.6,
    "output_variable": { "name": "faq_answer", "scope": "temp" }
  }
}
```

**⑤ http（HTTP 节点）— 新增**
```json
{
  "type": "http",
  "data": {
    "url": "https://api.example.com/order/{{session.order_id}}",
    "method": "GET",
    "headers": { "Authorization": "Bearer {{global.api_token}}" },
    "timeout": 5000,
    "output_variable": { "name": "order_info", "scope": "session" }
  }
}
```

**⑥ code（代码节点）— 新增**
```json
{
  "type": "code",
  "data": {
    "language": "javascript",
    "code": "const total = session.items.reduce((s, i) => s + i.price, 0); temp.total = total;",
    "input_vars": ["session.items"],
    "output_vars": ["temp.total"]
  }
}
```

**⑦ handoff（转人工节点）— 新增**
```json
{
  "type": "handoff",
  "data": {
    "reason": "{{session.handoff_reason}}",
    "summary_variable": "session.conversation_summary",
    "queue": "default"
  }
}
```

### 3.4 异常处理机制（借鉴 Genesys）

每个可交互节点（collect/confirm/llm/http）支持配置异常处理：

```json
{
  "error_handling": {
    "no_match": {
      "max_retries": 3,
      "retry_prompts": ["没理解，请再说一遍", "请换个说法"],
      "on_exceeded": { "action": "goto", "target": "node_fallback" }
    },
    "timeout": {
      "seconds": 30,
      "action": "goto",
      "target": "node_timeout_handler"
    },
    "validation_failed": {
      "max_retries": 2,
      "on_exceeded": { "action": "set_variable", "var": "session.valid", "value": false }
    }
  }
}
```

### 3.5 状态机扩展

在现有状态机基础上增加异常状态：

```
idle → collecting → confirming → executing → done
                ↘          ↘            ↘
              no_match    cancelled    transferred(handoff)
                ↘
              exceeded_max_retries → handoff
```

## 四、数据表设计

### 4.1 新增/修改表

#### ① `task_def` 扩展（现有表，增加字段）
| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | int | 版本号，每次发布+1 |
| `status` | varchar | draft/published/archived |
| `variables` | json | 任务级变量声明（session 作用域） |

#### ② 新增 `task_instance` 扩展字段
| 字段 | 类型 | 说明 |
|---|---|---|
| `temp_vars` | json | temp 作用域变量（每轮重置） |
| `session_vars` | json | session 作用域变量 |
| `trace` | json | 执行轨迹（节点 ID 序列 + 耗时） |

#### ③ 新增 `user_profile` 表（user 作用域持久化）
```sql
CREATE TABLE user_profile (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id VARCHAR(64) NOT NULL,
  bot_code VARCHAR(64) NOT NULL,
  variables JSON NOT NULL DEFAULT '{}',
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_bot (user_id, bot_code)
);
```

#### ④ 新增 `bot_variable` 表（global 作用域）
```sql
CREATE TABLE bot_variable (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  bot_code VARCHAR(64) NOT NULL,
  var_key VARCHAR(64) NOT NULL,
  var_value TEXT,
  var_type VARCHAR(16) DEFAULT 'string',
  description VARCHAR(255),
  UNIQUE KEY uk_bot_key (bot_code, var_key)
);
```

#### ⑤ 新增 `task_version` 表（版本管理）
```sql
CREATE TABLE task_version (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_code VARCHAR(64) NOT NULL,
  version INT NOT NULL,
  dsl JSON NOT NULL,
  status VARCHAR(16) DEFAULT 'draft',
  published_at DATETIME NULL,
  created_by VARCHAR(64),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_task_code (task_code)
);
```

## 五、接口契约

### 5.1 流程 DSL 读写

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/tasks` | 任务列表（支持分页、状态筛选） |
| `POST` | `/api/tasks` | 创建任务（保存草稿） |

| `GET` | `/api/tasks/:code/versions` | 版本历史 |
| `POST` | `/api/tasks/:code/rollback` | 回滚到指定版本 |

### 5.2 变量管理

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/tasks/:code/variables` | 获取任务变量声明 |
| `PUT` | `/api/tasks/:code/variables` | 更新变量声明 |
| `GET` | `/api/bot-variables` | 全局变量列表 |

### 5.3 执行与调试

| 方法 | 路径 | 说明 |

## 六、前端编辑器设计要点

### 6.1 画布交互
- 基于现有 Vue Flow，左侧节点面板按分类展示（流程控制/对话/AI/数据/业务）
- 节点属性面板支持变量选择器（下拉列出当前作用域可用变量）
- 表达式编辑器支持 `{{var}}` 语法高亮和自动补全

### 6.2 调试面板
- 内置对话模拟器（借鉴 Botpress Emulator）
- 执行轨迹可视化：节点高亮、变量实时值、耗时显示
- 单步执行/断点调试

### 6.3 版本管理
- 顶部显示当前状态（草稿/已发布）和版本号
- "发布"按钮生成新版本，"回滚"可选择历史版本

## 七、迁移路径（从 v2 到 v3）

采用**渐进式兼容**策略，不破坏现有任务：

### 阶段一：兼容层（1-2 周）
- flowConverter 增加 v2 DSL → v3 DSL 自动转换
- 变量引擎默认将 slots 映射为 session 作用域变量
- 现有 collect/confirm/action/branch/message/subtask 节点无需修改即可运行

### 阶段二：新节点上线（2-3 周）
- 新增 llm/knowledge/http/code/set_variable/handoff 节点
- 前端节点面板增加这些节点
- 后端节点注册中心支持动态注册

### 阶段三：变量体系升级（1-2 周）
- 引入 user/global 作用域
- 新增 user_profile / bot_variable 表
- 编辑器支持变量声明面板

### 阶段四：版本与可观测性（1-2 周）
- task_version 表与发布/回滚接口
- 执行轨迹采集与可视化

## 八、验证方式

### 8.1 单元测试
- 变量引擎：四级作用域读写、作用域隔离、模板解析
- 节点执行：每种节点类型的输入/输出/异常路径
- DSL 转换：v2 → v3 兼容性
- 状态机：异常状态转移（max_retries exceeded → handoff）

### 8.2 集成测试
- 端到端流程：含 llm + http + branch + collect 的复合流程
- 异常场景：No Match 重试耗尽 → 转人工
- 变量跨节点传递：temp → session → user 持久化

### 8.3 手动测试用例
1. 创建含 LLM 节点的意图分类流程，验证分类结果驱动分支
2. 配置 collect 节点 max_retries=2，连续输入无效值，验证转人工
3. 编辑流程 → 发布 → 回滚，验证版本切换
4. 设置 user 作用域变量，跨会话验证持久化

## 十、与 AGENTS.md 规约对齐检查

| 规约项 | 本方案合规性 |
|---|---|
| 前后端分离 | ✅ DSL 前后端共享，编辑器与执行器解耦 |
| 后端分层 | ✅ 路由 → schema → service → model 四层，节点执行在 service 层 |
| 配置与代码分离 | ✅ 阈值、模型、超时全部走 sys_config / bot_variable |
| 接口统一返回结构 | ✅ `{ success, data, message }` |
| 列表接口分页筛选 | ✅ `/api/tasks` 支持分页、状态筛选 |
| 字段全链路同步 | ✅ model → schema → 接口 → 前端 TS → 页面 同步设计 |
| 不破坏现有逻辑 | ✅ 渐进式迁移，v2 DSL 自动兼容 |
